# Load Context (세션 핸드오프 복원)

이전 세션이 슬러그로 저장한 핸드오프를 읽어, 그 작업이 걸친 repo(들)의 현재 상태와 대조한 뒤 브리핑한다. **자동으로 작업을 재개하지 않는다** — 사용자가 명시적으로 지시하면 그때 시작한다.

핸드오프는 자동 압축(대화 요약)을 대신하려고 만든 것이다. save-context는 다음 세션이 다시 알아낼 수 없는 것을 `## 놓치면 안 되는 것`에 골라 두었다. 그래서 브리핑은 짧게 하되 **그 칸만은 요약하지 않고 그대로 전한다.** 여기서 줄이면 압축과 똑같은 손실이 생긴다.

핸드오프의 단위는 repo가 아니라 작업(슬러그)이다. 한 작업이 여러 repo에 걸칠 수 있고, 그 repo 목록은 핸드오프의 `## 작업 repo (기준값)`(옛 양식은 머리말의 "작업 repo"·"관련 repo")에 있다.

## When to Use

- 새 세션에서 지난 작업을 이어갈 때
- 사용자가 "이어서 하자", "load context", "지난번 거 복원"을 요청할 때

## 준비 — 색인 스크립트와 저장소 위치

절차에 들어가기 전에 한 번 실행한다. 저장소 위치(옛 `~/.claude/agent-system` 호환 링크, `AGENT_SYSTEM_HOME` 설정)는 스크립트가 정하므로 스킬에서 경로를 직접 조립하지 않는다 — save-context와 다른 폴더를 읽으면 저장한 핸드오프가 "없다"고 나온다.
```bash
INDEX_SH="${CLAUDE_PLUGIN_ROOT:+$CLAUDE_PLUGIN_ROOT/scripts/handoff-index.sh}"     # Claude Code
[ -f "$INDEX_SH" ] || INDEX_SH="$HOME/.agent-system/bin/handoff-index.sh"         # Codex·Antigravity (setup.sh가 건 링크)
[ -f "$INDEX_SH" ] || { echo "handoff-index.sh를 찾을 수 없습니다 — 플러그인 폴더에서 ./setup.sh를 먼저 실행하세요" >&2; exit 1; }
echo "$INDEX_SH"; "$INDEX_SH" init     # 둘째 줄 = 저장소 경로(AS_HOME)
```
출력된 두 경로(`INDEX_SH`, `AS_HOME`)를 이후 명령에 절대경로로 그대로 쓴다. 명령마다 셸이 새로 떠서 변수가 이어지지 않는다.

## 절차

0. **어떤 핸드오프를 복원할지 고른다.** 핸드오프는 `<AS_HOME>/handoffs/<슬러그>.md`에 저장되고, 중앙 색인(`<AS_HOME>/handoffs.tsv`)이 그 목록을 모은다. 색인 컬럼은 `슬러그 \t 저장시각 \t 목표 \t 상태 \t 관련repo` 5개다.
   ```bash
   cat "<AS_HOME>/handoffs.tsv"
   ls "<AS_HOME>/handoffs/"*.md 2>/dev/null     # 색인에 없는 고아 파일 확인용
   ```
   - **사용자가 인자(슬러그 일부/목표 키워드)를 줬으면** 색인 1번째 칸(슬러그)과 대조해 하나로 좁힌다. 정확히 하나면 그걸 대상으로, 여럿이 맞으면 후보만 보여주고 고르게 한다.
   - **인자가 없으면:**
     - 색인 항목 0개 → "저장된 핸드오프가 없습니다."로 종료한다. (없는 것은 오류가 아니다)
     - 1개 → 그 항목을 대상으로 한다.
     - 2개 이상 → `번호) 슬러그 · 저장시각 · 목표 · 상태 · 관련repo` 목록을 사람이 읽기 좋게(표) 보여주고, 사용자가 번호를 고를 때까지 기다린다. **자동 선택 금지.** 오늘 날짜가 상태 칸의 약속("9/4 복귀")과 맞는 항목이 있으면 그 사실만 짚어 준다.
   - 목록을 보여줄 때 **정리 후보**를 함께 알린다: 저장시각이 30일 넘은 항목, 그리고 `handoffs/`에 있는데 색인에 없는 고아 파일. "끝났으면 보관할 수 있다"고 한 줄만 덧붙이고, 이동·삭제는 사용자가 시키기 전엔 하지 않는다.
   - **일괄 보관**: 사용자가 "오래된 것 정리해줘"처럼 요청하면 30일 넘은 목록을 뽑아 보여주고, 보관할 슬러그를 사용자가 확인한 뒤에만 옮긴다. 목록 중 일부만 고르면 그 슬러그만 넘긴다.
     ```bash
     "<INDEX_SH>" stale 30          # 슬러그 · 저장시각 · 상태
     "<INDEX_SH>" archive <슬러그> [<슬러그> ...]
     ```
     보관은 `handoffs/archive/`로 옮기는 것이고 삭제하지 않는다.

1. **핸드오프 파일을 읽는다.**
   ```bash
   cat "<AS_HOME>/handoffs/<슬러그>.md"
   ```
   - 색인엔 있으나 파일이 없으면(색인이 낡음): "색인엔 있으나 핸드오프 파일이 사라졌습니다"라고 알리고, 그 줄을 색인에서 지울지 제안한 뒤 다시 고르게 한다. 색인 줄 삭제는 `"<INDEX_SH>" remove "<슬러그>"`.
   - 색인이 아예 없으면: "저장된 핸드오프가 없습니다."로 종료한다.
   - 본문 `- 저장:` 시각과 색인 저장시각이 다르면 브리핑에 표시한다(어느 쪽이 나중 것인지 포함).

2. **현실 검증** — 핸드오프는 "쓰인 시점의 진실"이므로 현재와 대조한다.

   **작업 repo** 각각에 대해:
   ```bash
   "<INDEX_SH>" baseline <작업 repo> [<작업 repo> ...]       # 저장할 때와 같은 형식으로 지금 상태를 뜬다
   git -C <repo> log --oneline <핸드오프-커밋>..HEAD          # 저장 이후 커밋들 (주1)
   ```
   - **새 양식**(`## 작업 repo (기준값)`이 있음): 저장된 블록과 지금 출력을 **줄 단위로** 비교한다. 저장된 줄 끝의 ` ← 사용자`는 떼고 비교한다.
     - 머리줄(브랜치·커밋)이 다르면 저장 이후 브랜치가 바뀌었거나 커밋이 쌓인 것이다.
     - 미커밋 줄이 새로 생겼거나 같은 파일의 줄 수가 달라졌으면 "저장 이후 누가 더 만졌다"는 뜻이니 그 파일을 짚는다.
     - 저장된 미커밋 줄이 사라졌으면 커밋됐거나 되돌려진 것이다. 주1의 커밋 목록으로 어느 쪽인지 가린다.
   - **옛 양식**(머리말에 `작업 repo`·`관련 repo` 줄만 있음): 적힌 브랜치·커밋·미커밋 목록과만 비교한다. 줄 수 같은 기준값이 없으면 "기준값 없음 — 소유 구분 불가"로 표시하고 그럴듯하게 추정하지 않는다.
   - 주1: `<핸드오프-커밋>` 자리에는 그 repo의 저장 시점 short hash를 넣는다. 없으면 건너뛴다. 그 해시가 현재 히스토리에 없으면(rebase/squash/amend 등) "저장 시점 커밋을 현재 히스토리에서 찾을 수 없음"을 브리핑에 표시한다.

   **주변 repo**(있을 때): 적힌 "주의" 조건만 확인한다(예: 미추적 파일이 아직 있는지, stash가 살아 있는지). 브랜치나 커밋이 바뀐 것은 이 repo에선 경보가 아니다 — 작업 대상이 아니라서 넣은 항목이다. 옛 양식에서 "관련 repo"에 "이 작업 아님"이라 적힌 항목도 같은 취급을 한다.

   **외부 참조**(있을 때): PR/MR·Confluence·지라는 자동으로 조회하지 않는다(사내망·인증이 필요하고, 조회 자체가 부작용일 수 있다). 브리핑에 "저장 시점 상태 그대로, 지금은 미확인"으로 표시한다. 사용자가 확인을 원하면 그때 조회하되, 기준값의 `원격` 줄로 도구를 고른다 — GitHub면 `gh`, GitLab이면 `glab`, 기타면 어느 쪽인지 사용자에게 묻는다. 조회는 상태를 읽기만 하고, PR/MR 수정·코멘트는 사용자가 시킬 때만 한다.

   **파일 존재**: "놓치면 안 되는 것"·"다음 할 일"·"현재 상태"가 언급하는 로컬 파일·디렉토리가 실제로 존재하는지 확인하고, 없으면 표시한다. 코드 repo가 없는 조사 작업이면 git 대조는 건너뛰고 산출물·참조 파일 존재만 확인한다.

   **대조는 여기까지만 한다.** 핸드오프에 적힌 사실을 확인하려고 코드를 다시 읽고 조사하지 않는다. 관련 파일이 저장 이후 바뀌었으면 "저장 이후 바뀜 — 다시 확인 필요"만 적는다. load는 무엇이 달라졌는지 알리는 단계이고, 어디를 파고들지는 브리핑을 본 사용자가 정한다. 항목마다 재조사하면 몇 분씩 걸리고 브리핑이 원문보다 길어진다.

3. **브리핑한다.** 순서대로 제시한다:
   1. **놓치면 안 되는 것** — 핸드오프의 `## 놓치면 안 되는 것`을 **요약·생략 없이 그대로** 맨 앞에 보여 준다. save가 이미 7개 이내로 골라 둔 칸이라 그대로 옮겨도 짧다.
      - **옛 양식이라 이 칸이 없으면 save와 같은 기준으로 직접 고른다.** `결정 사항`·`주의사항`·`현재 상태`에서 1등급(다시 알아낼 수 없고 놓치면 사고나 반복이 생기는 것 — 사용자 지시·정정, 해봤는데 안 된 것과 원인, 조사로 확인한 사실, 건드리면 안 되는 파일, 답을 기다리는 것)만 **최대 7개**, 각각 한 줄로 줄여서 보여 주고 "옛 양식이라 본문에서 골라냄"이라고 밝힌다. 고르지 않은 것은 `나머지 결정 사항 N개·주의사항 M개는 핸드오프 원문에` 한 줄로 남긴다. 다 옮기면 중요한 항목이 다시 묻힌다 — save가 7개 상한을 두는 이유와 같다.
      - 옛 양식 주의사항 중 repo에 늘 해당하는 규칙(테스트·빌드 명령의 함정, 서버 띄우는 법 등)은 1등급에 넣지 않고 5번에서 한 줄로 알린다.
      - 항목이 지금 상태와 어긋나면 바로 옆에 짧게 적는다. 2단계에서 본 것(파일 존재, git 상태)으로만 판단한다.
   2. 목표 / 현재 상태 / 다음 할 일. 다음 할 일은 "왜"까지 같이 옮긴다 — 근거를 떼고 옮기면 사용자가 "그건 왜 하는데?"를 다시 묻게 된다.
   3. 검증 결과 — 작업 repo가 여럿이면 repo별로. 주변 repo는 "주의 조건 유효/해소"만. 핸드오프와 다른 점은 구체적으로("저장 이후 커밋 3개", "a.ts가 저장 시점 +2줄에서 지금 +15줄 — 누가 만졌는지 확인 필요").
   4. 외부 참조는 "저장 시점 상태, 지금은 미확인" 표시와 함께.
   5. `(AGENTS.md 후보)`로 남은 규칙, 또는 옛 양식에서 repo 규칙으로 보이는 주의사항이 있으면 한 줄: 몇 개인지와 AGENTS.md로 옮길 수 있다는 것(옮기지 않으면 작업이 끝날 때 핸드오프와 함께 묻힌다).
   6. 정리 후보(30일+, 고아 파일)가 있었으면 한 줄.
   7. 마지막 줄에 `핸드오프: <AS_HOME>/handoffs/<슬러그>.md` — 대화가 압축돼도 이 경로가 남아 다시 읽을 수 있다.

   짧게 줄이는 것은 2~6번에만 해당한다. 브리핑 전체는 한 화면(대략 50줄) 안을 목표로 한다. 그보다 길어지면 대개 저장 이후 바뀐 점이 아니라 핸드오프 원문을 옮기고 있는 것이다.

4. **지시를 기다린다.** 자동으로 다음 할 일을 실행하지 않는다.

## 이어서 작업하는 동안

- **다음 할 일 항목에 손대기 직전**, 그리고 **대화가 압축된 뒤**(대화 첫머리가 이전 대화 요약으로 바뀜)에는 핸드오프 파일을 다시 읽는다. 처음 읽은 핸드오프는 도구 출력으로만 대화에 들어와 있어서, 세션이 길어져 압축되면 다른 내용과 함께 뭉개진다 — 이 스킬이 막으려던 바로 그 손실이다. 핸드오프는 100줄 안팎이라 다시 읽는 비용은 작다.
- `놓치면 안 되는 것`의 지시·금지(예: "이 명령 대신 저 명령", "이 파일은 건드리지 말 것")는 그 작업을 하기 직전에 다시 확인한다.

## 원칙

- 핸드오프 내용을 그대로 믿지 말고 항상 현재 상태와 대조한다. 오래됐거나 다른 머신/세션의 작업이 끼어들었을 수 있다.
- **읽은 것·검증한 것만 전달하고, 빈칸을 추측으로 메우지 않는다.** 핸드오프에 없거나 모호한 부분을 그럴듯한 해석으로 단정하지 말 것. 핸드오프와 현재 상태가 서로 다르거나 불명확하면 매끄럽게 넘기지 말고 "불명확/검증 필요"로 드러낸다. 추론을 전할 땐 확인된 사실과 구분해 표시한다.
- 브리핑은 짧게 — `놓치면 안 되는 것`만 예외다. 다음 할 일의 첫 항목을 또렷하게 전달한다. 나머지는 요약하되, 서로 다른 점과 "왜"는 줄이지 않는다.
