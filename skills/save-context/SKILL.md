# Save Context (세션 핸드오프 저장)

현재 세션의 작업 상태를 슬러그(보통 지라 키)로 식별되는 핸드오프 파일 하나로 중앙 저장소에 써, 다음 세션이 슬러그를 골라 이어받을 수 있게 한다.

핸드오프의 단위는 repo가 아니라 **작업(슬러그)**이다. 그래서 (a) 한 repo에서 여러 작업을 번갈아 해도 서로 덮어쓰지 않고, (b) 한 작업이 여러 repo에 걸쳐도 핸드오프 하나에 모을 수 있다.

핸드오프를 읽는 쪽(load-context)은 **본문을 현재 repo 상태와 대조**한다. 그래서 이 스킬이 남기는 것은 요약이 아니라 "저장 시점의 기준값"이다. 기준값이 없으면 다음 세션은 무엇이 바뀌었는지 확인할 수 없다.

## When to Use

- 오늘 작업을 끝내고 내일 이어서 할 때
- 컨텍스트 한도가 차서 새 세션으로 넘어가야 할 때
- 사용자가 "컨텍스트 저장", "핸드오프 정리", "save context"를 요청할 때
- 저장해 둔 작업이 끝나서 목록에서 치우고 싶을 때 → 아래 "완료 처리"

## 절차

1. **슬러그를 정한다.** 슬러그는 이 작업을 식별하는 짧은 이름이자 파일명이 된다. 영문/숫자/`-`/`_`만 쓰고 소문자로 통일한다(공백→`-`).
   - 사용자가 인자를 줬으면 그걸 슬러그로 쓴다 (`save-context soopkr-29478` → `soopkr-29478`).
   - 안 줬으면 현재 브랜치에서 유도한다 — prefix를 떼고 소문자화(`feature/soopkr-29935` → `soopkr-29935`).
   - 브랜치가 `master`/`main`/`develop`/`staging` 같은 일반명이라 작업을 식별하지 못하면, 지어내지 말고 사용자에게 슬러그를 한 번 물어본다.
   - 같은 슬러그 파일이 이미 있으면 그 파일을 먼저 읽는다. 지난 내용 중 여전히 맞는 것은 이어 쓰고, 끝난 것은 "현재 상태"로 옮긴다(아래 템플릿 원칙 참조).

2. **작업 repo와 주변 repo를 가른다.**
   - **작업 repo** = 이 작업으로 파일을 바꾼(바꿀) repo. 보통 하나, 여러 개면 각각.
   - **주변 repo** = 이 작업 대상은 아니지만 다음 세션이 실수로 건드리면 안 되는 이웃(예: 다른 작업의 stash 짝인 미추적 파일이 있는 repo). 여기에 넣는 이유는 **경고를 남기기 위해서**고, load-context는 이 repo의 브랜치·커밋 변화를 경보로 취급하지 않는다. 작업 repo에 섞어 넣으면 다음 세션이 무관한 브랜치 변경에 놀란다.
   - 코드를 안 건드린 조사·문서 작업이면 작업 repo를 비우고 "(조사 — 코드 미수정)"이라 적는다.

3. **작업 repo마다 기준값을 뜬다.** 브랜치·커밋만으로는 부족하다. 미커밋 변경은 다음 세션에 "내가 남긴 것인지, 그 사이 사용자가 더 만진 것인지"를 가르는 핵심 증거라 목록과 규모를 그대로 적어 둔다:
   ```bash
   NOW="$(date '+%Y-%m-%d %H:%M')"                              # 본문·색인에 같은 값을 쓴다
   git -C <repo> rev-parse --abbrev-ref HEAD 2>/dev/null        # 브랜치
   git -C <repo> log -1 --pretty='%h %s' 2>/dev/null            # 마지막 커밋 (해시 + 제목)
   git -C <repo> status --short 2>/dev/null                     # 미커밋 파일 목록 (그대로 붙인다)
   git -C <repo> diff --stat 2>/dev/null | tail -1              # 미커밋 규모 한 줄
   ```
   미커밋 파일 중 **내 세션이 만든 것과 사용자 것이 섞여 있으면 파일 단위로 갈라 적는다**. "한 줄만 내 것"처럼 규모를 말로 적지 말고 `diff --stat`의 숫자를 남긴다 — 말로 적은 규모는 나중에 대조가 안 된다.
   git repo가 아니면 브랜치/커밋 줄은 생략한다.

4. **아래 템플릿으로 핸드오프 파일을 쓴다.** 같은 슬러그면 그 파일만 덮어쓴다(다른 작업 파일은 건드리지 않는다). 덮어쓸 때 `- 저장:` 줄도 반드시 `$NOW`로 다시 찍는다 — 본문 시각이 옛것으로 남으면 색인 시각과 서로 달라 어느 쪽이 정본인지 헷갈린다. 필수 4섹션은 항상, 선택 3섹션은 해당 내용이 있을 때만. 빈 섹션을 억지로 남기지 않는다:
   ```bash
   DIR="$HOME/.claude/agent-system/handoffs"; mkdir -p "$DIR"
   # 파일: $DIR/<슬러그>.md
   ```

5. **중앙 색인을 갱신한다.** load-context가 목록으로 보여주는 한 줄이다. 컬럼 5개: `슬러그 \t 저장시각 \t 목표 \t 상태 \t 관련repo`.
   - `목표` = `## 목표` 첫 줄. 작업이 끝나면 무엇이 돼 있어야 하는지. 저장할 때마다 바뀌지 않는다.
   - `상태` = 지금 어디까지 왔고 다음 할 일이 무엇인지 한 줄. 저장할 때마다 바뀐다. 사람이 목록에서 "어느 걸 이어서 할지" 고르는 데 실제로 쓰는 칸이라 날짜 약속("9/4 복귀 후 확인")이 있으면 여기에 넣는다.
   - `관련repo` = 작업 repo basename을 쉼표로(없으면 `-`). 주변 repo는 넣지 않는다.
   ```bash
   "${CLAUDE_PLUGIN_ROOT}/scripts/handoff-index.sh" upsert "$SLUG" "$NOW" "<목표 한 줄>" "<상태 한 줄>" "<repo basename들>"
   ```
   스크립트가 같은 슬러그 줄을 지우고 새 줄을 넣는다. 칸 값의 탭·줄바꿈은 공백으로 바꾸므로 TSV 칸 수가 틀어지지 않는다. 쓰기 전 색인을 `handoffs.tsv.bak` 하나로 복사해 둔다(이전 `.bak`은 덮어씀). 색인은 목록용 요약일 뿐 정본은 `handoffs/<슬러그>.md`다. 색인·핸드오프 모두 로컬 전용이다.

6. **커밋하지 않는다.** 파일만 쓴다.

7. 저장한 슬러그와 파일 경로, 색인의 상태 한 줄을 사용자에게 알린다.

## 완료 처리 (보관)

작업이 끝났다고 사용자가 말하면(`save-context --done <슬러그>`, "kuro 끝났어 보관해줘") 핸드오프를 보관함으로 옮기고 색인에서 지운다. 색인은 "이어서 할 것"의 목록이라, 끝난 것이 남아 있으면 고를 때마다 전체를 다시 읽어야 한다.

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/handoff-index.sh" archive "$SLUG"     # 여러 개면 슬러그를 이어서 적는다
```
`handoffs/<슬러그>.md`를 `handoffs/archive/`로 옮기고 색인 줄을 지운다.

보관 전에 본문 "다음 할 일"에 남은 항목이 있으면 그 사실을 사용자에게 한 번 보여준다(남은 일이 다른 티켓으로 넘어갔는지 확인). 삭제는 하지 않는다 — 보관함은 나중에 "그때 왜 그렇게 했지"를 찾는 용도로 남긴다.

## 핸드오프 템플릿

```markdown
# HANDOFF: <슬러그>

- 저장: <YYYY-MM-DD HH:MM>   <!-- 덮어쓸 때마다 갱신, 색인과 같은 값 -->
- 작업 repo:
  - <repo경로> · <branch> · <shorthash 제목>
    - 미커밋: <git status --short 그대로. 없으면 "없음">
    - 규모: <git diff --stat 마지막 줄. 내 것/사용자 것이 섞였으면 파일별로 누구 것인지>
  - <repo가 여러 개면 항목 추가>   <!-- 코드 안 건드린 조사면 "(조사 — 코드 미수정)" -->
- 주변 repo:   <!-- 선택: 작업 대상은 아니지만 건드리면 안 되는 이웃이 있을 때만 -->
  - <repo경로> · 주의: <무엇을 하면 안 되고 왜> <!-- 예: 미추적 X는 다른 작업 stash의 짝 → git clean 금지 -->

## 목표
<이 작업이 끝나면 무엇이 되어 있어야 하는가 — 1~3줄. 색인의 목표 칸과 같은 첫 줄>

## 현재 상태
<어디까지 했고 지금 동작하는가. 이번 세션에 끝낸 것은 여기로. 검증 로그·수치 나열은 정본(Confluence/wiki/지라)에 두고 여기엔 결론과 포인터만>

## 다음 할 일
1. <바로 실행 가능한 첫 항목 — 파일/명령 수준으로> — 왜: <이 항목이 필요한 근거 한 줄>
2. <그다음> — 왜: <...>

## 외부 참조   <!-- 선택: MR·Confluence·지라 등 repo 밖 상태가 있을 때만 -->
- MR: <URL 또는 !번호(repo)> · 저장 시점 상태: <Draft/열림/머지됨/닫힘>
- Confluence: <페이지ID 또는 x/짧은키> · v<N> · <무슨 문서>
- Jira: <KEY> · <상태>

## 결정 사항   <!-- 선택: 다시 논쟁하지 않도록 정한 것이 있을 때만 -->
- <무엇을 왜 그렇게 정했나>

## 주의사항   <!-- 선택: 주의 사항·미해결 이슈·건드리면 안 되는 것이 있을 때만 -->
- <주의할 점>
```

## 작성 원칙

- **다음 할 일에는 "왜"를 붙인다.** "넥슨·크래프톤 연동도 함께 확인(리뷰 3번)"처럼 출처만 적으면 다음 세션은 "왜 그게 영향 범위인지"를 코드에서 다시 찾아야 한다. "왜: 게임 타입 추출 함수 내부가 바뀌었고, 기존 연동 생성 경로도 그 함수를 호출한다"처럼 근거를 한 줄 두면 그 조사가 사라진다. 이유가 정말 자명한 항목(단순 후속 단계)은 생략해도 된다.
- **끝난 항목은 취소선으로 남기지 않는다.** 완료분은 "현재 상태"로 옮기고 다음 할 일 번호를 다시 매긴다. 취소선은 읽는 쪽이 "아직 할 일인가"를 매번 판단하게 만든다.
- **검증 안 된 것을 사실처럼 적지 않는다.** 세션에서 실제로 일어났거나 확인된 것만 단정형으로 쓴다. 불확실한 추정은 `추정:`·`미확인:` 꼬리표를 달거나 "확인 필요"로 남기고, 그럴듯하게 지어내 빈칸을 채우지 않는다.
- **외부 상태는 "저장 시점 상태"를 명시한다.** MR이 머지됐는지, 문서가 몇 판인지는 다음 세션이 자동으로 확인할 수 없다(사내망·API). 시점을 적어 두면 적어도 "그 뒤로 바뀌었을 수 있다"는 판단은 할 수 있다.
- **부실 금지 / 장황 금지** 둘 다 피한다. 핸드오프가 100줄을 훌쩍 넘기면 대개 "현재 상태"에 검증 로그가 들어간 신호다. 그 상세는 정본 문서로 보내고 포인터를 남긴다. 반대로 "다음 할 일"의 첫 항목은 다음 세션이 즉시 손댈 수 있을 만큼 구체적이어야 한다.
- 같은 슬러그의 기존 핸드오프가 있으면 그 파일만 통째로 덮어쓴다(다른 슬러그 파일은 건드리지 않는다).
