# 동작 2: 기록·편입 (Ingest & Compile — 위키에 지식 쌓기)

새로 알아낸 아키텍처, 트러블슈팅 해결 과정, 도메인 스펙, 또는 완료된 핸드오프(`save-context --done`)에서 건져 올린 지식을 위키에 반영할 때 수행한다. [SKILL.md](../SKILL.md)의 "준비"를 마쳐 `$WIKI_SH`와 `WIKI=`(가까운 순)·`GLOBAL_WIKI=` 값을 확인한 상태에서 시작한다.

## 0단계: 넣을 위키가 없으면 연결하거나 만든다

1단계에서 고를 위키가 `WIKI=` 줄에 없으면(예: 이 repo 전용 지식인데 repo 위키가 아직 없음, 또는 `WIKI=` 줄이 아예 없음) 새 문서를 기록하기 전에 사용자에게 먼저 묻는다: **이 위치가 이미 있는 위키를 써야 하는 곳인가, 새 위키가 필요한 곳인가.**

- **이미 있는 위키를 써야 하는 곳**(예: 위키가 있는 폴더 바깥에 만든 worktree·작업 폴더 — repo 안에 만든 worktree는 위로 올라가며 찾으므로 해당하지 않는다): `"$WIKI_SH" links`와 전역 등록 목록(`<GLOBAL_WIKI>/roots.tsv`)에서 후보 위키를 보여 주고, 사용자가 고른 위키로 연결한다. 그 경로 아래 전체에 적용되며, 연결한 위키가 놓인 폴더의 위쪽 위키들(예: repo 위키를 연결하면 그 repo를 담은 상위 폴더의 위키)도 함께 조회된다. 그래서 보통은 가장 가까운 위키(repo 위키) 하나만 연결하면 된다:
  ```bash
  "$WIKI_SH" link <연결할경로> <위키루트>
  ```
- **새 위키가 필요한 곳**: 위키의 적용 범위가 될 폴더를 사용자에게 확인한 뒤 초기화한다 — repo 하나 전용이면 그 repo 루트, 여러 repo 공통이면 그 상위 폴더:
  ```bash
  "$WIKI_SH" init <경로>
  ```

만들 위치가 git repo 안이면(`git -C <경로> rev-parse --show-toplevel` 성공) 위키를 git에서 어떻게 다룰지도 함께 묻고, 답에 맞춰 같은 명령에 옵션을 붙인다:
- 기본(옵션 생략) = 이 기기에서만 무시 → `--ignore local`과 같음 (`.git/info/exclude`에 추가, repo 파일은 바뀌지 않음 — 회사·팀 repo에 개인 위키를 둘 때, 또는 상위 폴더 자체가 다른 repo일 때)
- 팀 전체가 무시 → `--ignore shared` (repo 루트 `.gitignore`에 추가, 이 변경은 커밋해야 함)
- repo에 같이 커밋 → `--ignore none` (무시 설정을 하지 않음. worktree에서도 보인다)
- 무시(local·shared)하면 위키가 git으로 백업되지 않고 worktree에도 들어오지 않는다(위키 폴더 바깥에 만든 worktree에서는 `link` 필요)는 점을 함께 알린다. 이미 만든 위키에 같은 `init` 명령을 다시 실행하면 기존 내용은 그대로 두고 무시 설정만 추가된다(옵션 없이도 local이 추가된다). 단 위키 파일이 이미 git에 커밋돼 있으면, 옵션 없이 실행할 때는 무시 설정을 건너뛰고 그렇다고 안내한다(커밋한 위키에 새 문서가 git에서 안 보이게 되는 것을 막기 위함). `--ignore local`·`--ignore shared`를 직접 붙이면 무시 설정을 추가하되, 이미 추적 중인 파일은 계속 추적되고 새로 만드는 위키 파일만 무시된다고 경고하며 기존 파일 추적을 끊는 `git rm -r --cached` 명령을 함께 출력한다. 그 명령의 실행 여부는 사용자에게 확인한다.

## 1단계: 어느 위키에 넣을지 결정한다
**이 지식이 적용되는 모든 곳을 덮는 가장 가까운 위키**를 고른다:
- **이 repo에서만 쓰는가?** → 이 repo의 `<repo>/docs/wiki`
- **같은 상위 폴더 아래 여러 repo가 함께 쓰는 도메인/인프라인가?** → 그 상위 폴더의 `docs/wiki`
- **회사·개인 무관하게 어디서나 쓰는 범용 기술/인프라 지식인가?** → `<GLOBAL_WIKI>`
- 애매하면 사용자에게 한 줄로 어느 위키에 넣을지 확인한다.

## 2단계: 기존 문서가 있는지 먼저 확인한다 (컴파일 원칙)
- **LLM Wiki의 핵심은 "무작정 새 파일로 쌓지 않고 기존 문서를 최신 상태로 컴파일(병합·갱신)하는 것"이다.**
- `"$WIKI_SH" list .`로 같은 주제의 문서가 이미 있는지 본다:
  - **이미 있으면**: 기존 `.md` 파일을 먼저 읽고, 새로운 내용을 기존 구조에 자연스럽게 병합·갱신한다. 시대에 뒤떨어진 옛 설명은 고친다.
  - **없으면**: `<위키루트>/<카테고리>/<문서명>.md` (예: `troubleshooting/cdn-cache-miss.md`, `architecture/auth-flow.md`, `infra/oci-setup.md`) 경로로 새 파일을 만든다. 카테고리 폴더는 `architecture`, `troubleshooting`, `domain`, `infra`, `guides` 등 직관적인 영문 소문자를 쓴다.

## 3단계: 위키 문서 작성 양식
문서 상단에 핵심 요약과 갱신일을 두고, 본문은 나중에 읽는 에이전트와 사람이 즉시 이해할 수 있게 구조화한다:

```markdown
# <문서 제목>

- **갱신일**: <YYYY-MM-DD>
- **태그**: `<태그1>`, `<태그2>`
- **요약**: <이 문서가 다루는 핵심 내용 한 줄 요약>

---

## 배경 / 핵심 요약
<왜 이 구조/문제가 생겼고 결론이 무엇인지 3~5줄 이내로 요약>

## 상세 내용
<아키텍처 흐름, 설정값, 코드 위치(`경로:줄번호` 또는 파일 경로), 원인 분석, 해결 단계 등>

## 주의사항 · 관련 문서
- <건드리면 안 되는 설정이나 함정>
- 관련 문서: [같은 위키의 다른 문서](../infra/xxx.md)
```

## 4단계: 색인(`wiki.tsv`), 목차(`index.md`), 변경 이력(`log.md`) 동기화
문서 파일을 저장한 뒤 **반드시** 아래 명령을 실행해 색인과 `index.md`, `log.md`를 자동 갱신한다 (`index.md`를 수동으로 편집하지 않는다). 슬러그는 `<카테고리>/<문서>` 형식이어야 하고 `.`·`..` 경로 조각을 쓸 수 없다(스크립트가 거부한다). 전역이 아닌 위키에 처음 `upsert`하면 다른 위치에서도 `search`되도록 전역 목록(`roots.tsv`)에 등록된다:

```bash
NOW="$(date '+%Y-%m-%d %H:%M')"
"$WIKI_SH" upsert "<위키루트>" "<카테고리/문서(확장자 제외, 예: troubleshooting/cdn-cache-miss)>" "$NOW" "<제목>" "<한 줄 요약>" "<쉼표로 구분한 태그>"
```
